1.  PRODUCT  DIRECTION  
Core  Positioning  
Jnanana  is  being  positioned  as:  
Building  the  World's  Largest  Mentorship  Program  
The  first  version  of  Jnanana  is  not  a  community  platform .  
The  core  product  experience  is:  
User  →  Discover  Mentor  →  View  Mentor  Profile  →  Use  Jule  Tokens  →  
Request
 
Mentorship
 
→
 
Connect
 
Everything  developed  in  Phase  1  should  support  this  core  experience.  
 
2.  PHASE  1  OBJECTIVE  
The  objective  of  Phase  1  is  to  build  a  simple,  stable,  deployable  MVP  that  can  be  used  during  
a
 
real
 
event.
 
The  system  must  be:  
--- PAGE ---
●  Simple  ●  Fast  ●  Lightweight  ●  Easy  to  understand  ●  Mobile-friendly  ●  Easy  to  operate  from  the  admin  side  ●  Deployable  to  production  ●  Stable  enough  for  live  event  usage  
We  should  NOT  attempt  to  build  the  complete  long-term  Jnanana  ecosystem  in  Phase  1.  
 
3.  IMPORTANT  DEVELOPMENT  
PRINCIPLE
 
Build  →  Deploy  →  Test  Live  →  Observe  →  Improve  
The  first  version  must  be  deployed  and  tested  with  real  users.  
The  technology  team  should  avoid  spending  excessive  development  time  on  features  that  have  
not
 
yet
 
been
 
validated.
 
If  a  feature  is  not  explicitly  included  in  Phase  1  of  this  document,  it  should  not  be  added  to  the  
MVP
 
unless
 
approved
 
separately.

13.  JULE  TOKEN  SYSTEM  
Jule  Tokens  are  the  initial  mechanism  for  mentorship  transactions.  
The  system  must  maintain  a  token  balance  for  every  participating  user.  
Example:  
Jule  Balance:  50  
 
14.  INITIAL  TOKEN  ALLOCATION  
For  every  confirmed  event  participant:  
--- PAGE ---
Base  Allocation  
50  Jule  Tokens  
are  allocated  to  the  participant.  
The  Admin  should  be  able  to  perform  this  allocation  automatically  or  manually.  
 
15.  ADDITIONAL  TOKEN  POOL  
An  additional:  
50  Jule  Tokens  
may  be  distributed  through  event  activities,  professional  engagement,  participation,  or  other  
approved
 
activities.
 
This  should  be  controlled  by  the  Admin.  
The  Admin  must  be  able  to:  
Add  Tokens  
and  
Deduct  Tokens  
from  a  user.  
 
16.  TOKEN  TRANSACTION  LOG

45.  CRITICAL  PRODUCT  RULES  
Rule  1  
Do  not  build  unnecessary  features.  
If  it  does  not  contribute  to  the  core  mentorship  flow,  it  should  not  be  part  of  the  MVP.  
 
Rule  2  
Mentorship  is  the  primary  product.  
Do  not  position  or  architect  the  first  version  primarily  as  a  community  platform.  
 
Rule  3  
Event  is  the  first  real-world  validation  environment.  
The  product  must  be  ready  to  be  used  by  actual  attendees.  
 
Rule  4  
Mentors  are  initially  curated.  
The  Admin  assigns  mentors  to  events.  
 
--- PAGE ---
Rule  5  
Mentor  profiles  are  initially  created  by  Admin.  
Mentors  can  subsequently  update  their  information.  
 
Rule  6  
Jule  Tokens  must  be  traceable.  
Every  addition  and  deduction  must  have  a  transaction  record.  
 
Rule  7  
The  first  version  should  remain  lightweight.  
Do  not  introduce  automation  where  manual  operations  are  sufficient  for  MVP  validation.
